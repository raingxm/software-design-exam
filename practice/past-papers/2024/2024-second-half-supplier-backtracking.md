# 2024 年下半年 · 算法 C · 多供应商部件采购回溯

> 来源：刷题 App 截图（标注“2024 年下半年”）
> 状态：问题 1 代码填空已完成（2026-09-07 · 4/5 独立答对，第 4 空订正）

## 题目摘要

机器由 `n` 个部件组成，每个部件可从 `m` 个供应商中选择。供应商 `j` 提供的部件 `i` 有重量 `w[i][j]` 和价格 `c[i][j]`；要求在总价格不超过 `cc` 的条件下，使机器总重量最小。

代码采用深度优先回溯：逐个部件枚举供应商，维护当前方案 `x`、累计重量 `cw` 和累计价格 `cp`，通过价格上限和当前最优重量进行剪枝。

## 问题 1 · 填空与订正

```c
(1) bestX[j] = x[j]
(2) j < m
(3) x[i] = j
(4) cw < bestW
(5) cp = cp - c[i][j]
```

- 独立答对 `(1)(2)(3)(5)`。
- `(4)` 初答 `cw <= bestW`，逻辑上通常仍能算出最小重量，但会继续搜索不能改善答案的等重分支；标准剪枝应为严格小于 `cw < bestW`。
- 已理解 `j < n` 与 `j < m` 的区别：前者遍历部件以保存方案，后者遍历供应商以枚举选择。
- 已理解回溯恢复：`cw`、`cp` 是跨层累计状态，尝试兄弟分支前必须撤销；`x[i]` 会在同层下一轮被覆盖，无须清零。

## 代码语义缺陷：`found` 会误报完整解

原代码包含：

```c
if (cp <= cc) {
    found = 1;
}
```

`cp <= cc` 只说明当前**部分方案暂未超预算**，不能说明已经选完全部部件并得到完整可行解。

最小反例：只有 1 个部件和 1 个供应商，价格为 5、上限为 4。根结点处 `cp = 0 <= 4`，原代码会先令 `found = 1`；唯一选择随后超预算，实际没有完整解，但函数仍返回 1。

这不一定破坏本题 `bestW/bestX` 的更新，因为答案只在 `i > n - 1` 的完整叶结点写入；但它使 `backtrack()` 的布尔返回值不可信。若 `found` 表示“子树内找到完整可行解”，应删除上述提前赋值，仅在到达完整叶结点时返回 1，再逐层向上传播。

## 回溯阅读口令

```text
记录选择 → 累加状态 → 约束/最优性剪枝 → 递归 → 撤销累计状态 → 尝试兄弟分支
```

最小化问题的剪枝口令：**当前重量已经不小于已知最优重量，就不可能改善答案。**

## 晚上续学入口

1. 闭卷复述 `x / bestX / cw / cp / bestW` 的职责。
2. 手推给定 `3 × 3` 数据的搜索过程，找出价格不超过 4 的最小重量方案。
3. 判断最坏时间复杂度，并说明为什么剪枝不改变最坏复杂度的数量级。
4. 把有缺陷的 `found` 逻辑改写为“仅完整叶结点才算找到解”。
